# D-036 — One reviewed synthetic preparation pack

Status: **Proposed. No publication authority or implementation is approved by this record.**
D11-A is documentation only, based on main `953d49ece70f7828935bb0f4636299d7601f16d5`
(normal merge of PR #32, reviewed head `4f86e2f5`). D10-B is merged. D11-B requires
explicit human acceptance of the boundary below before implementation.

## Decision requested

Permit one server-validated, versioned **preparation-only** Organization Runtime Pack
for “prepare and coordinate an evidence-backed invoice-dispute disposition.” A fixed
synthetic publication reviewer may explicitly select an exactly reviewed artifact for
future scoped read/propose work. Retain that approval and selection history in one
append-only PostgreSQL supporting journal. Publishing does not run a step, activate
the ECC graph, attach the pack to a Case, confer business authority or enroll intake
Cases into D-033. D12 integrates one worker only after its applicable contracts pass review.

The new trust boundary is **descriptive material → separately approved preparation
configuration**. D-035 confirmation is a prerequisite input, never that approval.
The proposed reviewer can approve preparation configuration, supersede it or withdraw
its current selection; cannot approve business source precedence, financial policy,
action, outcome acceptance, real-data access or closure. No general Builder, policy
editor, workflow language, additional Case model or authority engine is proposed.

Human approval of D-036 would authorize this narrow D11-B implementation; it would
not publish the example or approve any individual future pack. D-034/D-035 approval
history, D-013 closure denial, D-014 Case versions and D-032/D-033 remain unchanged.

## Useful assignment and populated example

[The proposed JSON artifact](../examples/d11-invoice-dispute-pack.proposed.json)
contains the complete four-step contract, seven records, six loop outputs, source
citations, disabled rules, proof/correction requirements and exact basis bindings.
Its proposed format is ordinary JSON, **not a registered runtime contract**. The
wrapper's `artifact_hash` is the existing `sha256Json(artifact)`; it excludes only the
wrapper, not any artifact field. The wrapper’s `example_basis_export_hash` checks
the test reproduction only: full exports contain command bookkeeping and do not
form the pack consent hash. Arrays retain their specified order. No timestamps,
IDs or approval receipts are generated by a preview. D11-B must reject duplicate
keys, unknown properties, noncanonical values and unsupported versions before use.

The populated basis was produced through the existing disposable PostgreSQL/API
helper, with fixed synthetic inputs/time/keys; reproduce it below. North
`dispute-17` reports **$15,000 USD in dispute**, Orchid, INV-101, PO-9 and DEL-4.
The associated note reports that delivery confirmation is not supplied. It does
not prove non-delivery, the customer's impact, or that a $15,000 credit is justified.
Taylor is a reported upstream owner, not a canonical accountable identity.
South `dispute-18` reports $2,500 against the same invoice label; it is separate context.

The proposed compact packet, using the current Workbench layout, reads:

> **Orchid — prepare an invoice-dispute disposition**
>
> North dispute-17 reports $15,000 in dispute. The DEL-4 note reports missing
> confirmation; governing terms and customer impact remain unconfirmed.
>
> **Prepared:** linked queue row, associated note, scoped gap questions.
>
> **Next:** identify who can supply DEL-4 proof and governing terms; inspect the
> citations and correct the description. Evidence/business owner is unconfirmed.
>
> **Preparation reviewer:** synthetic intake operator. Financial action unavailable.
>
> Expand sources, related records, versions and history.

A proposed pack-review view adds a content diff, unresolved requirements and an
explicit **Publish for preparation** control for the separate synthetic publication
seat. A descriptive Confirm control never becomes Publish. D11-A adds neither UI.

### Simplify before allocating

| Change to the proposed route                                                    | Control retained                                                        | Mechanism after simplification                                               |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Remove repeated copying into another worksheet.                                 | Original bytes, record key/revision and locators.                       | Code binds and indexes existing retained inputs.                             |
| Combine separate evidence requests into one scoped agenda.                      | Each question retains its subject, applicability and uncertainty.       | Code derives gaps; a person confirms recipients and consequential questions. |
| Collect delivery proof and governing terms in parallel where independent.       | Owners/access first; no message dispatch; do not sum overlapping waits. | People collect approved material; later worker may prepare requests.         |

The four retained steps are S1 bind/inspect → S2 compare/ask → S3 human descriptive
review → S4 draft disposition packet. S2 can continue listing unaffected findings
while S3 seeks proof. S4 can produce a useful **gap packet** while abstaining from a
recommended disposition. The JSON specifies inputs, outputs, acceptance, dependencies,
accountable/exception owners, allowed actions, stops and evaluations for each step.
The synthetic support seat is a proposed demo responsibility, not evidence that Taylor
or a real business owner accepted work. No business due date or escalation SLA is known.

Structured input and a small literal-text interpreter justify **zero model calls**.
There is no need for an adaptive agent to search a fixed retained bundle. A later
bounded model may propose interpretations of selected ambiguous parsed text only if
code is inadequate, with citations, a strict output, abstention and human review;
it cannot parse retained-only material implicitly. D12 must justify and bound any
such task's tools, calls/steps, time and cost before integration. No agent loops,
provider dependency or worker dispatch belongs to D11-B.

### Complete requirements without inventing evidence

R1–R7 in the JSON explicitly retain unknown normal route/start; cohort/exception
rates; dependency owners/deadlines; field precedence; regional/entity/acquisition
variants; elapsed/active/wait/handoff measurements; and task-specific readiness/support.
The six outputs are Trigger, Objective, Population, Close Event, Human Intervention
Map and Correction Path. Their proposed or unknown state is preserved; membership
in a pack is not evidence of completeness. Documented, observed and proposed process
remain distinct, as do evidence type and review status.

Use the existing source material, not invoice labels, to scope every comparison:
record facts keep `(tenant, entity, record_key/source revision)`; delivery claims keep
`(entity, delivery ID)` **and explicit source associations/applicable record keys**.
Different amounts on different records are not contradictions. Explicitly shared
object evidence can apply to several records, subject to the whole artifact's read
scope. Unknown association remains ambiguous. PDF/image retention is not parsing.
A queue snapshot cannot establish a historical route, waiting time or active effort.

Missing bytes, trusted scope, valid locator or supported interpreter blocks the
preparation depending on it. Missing delivery proof/terms allows a cited question,
but blocks a supported disposition conclusion. Missing policy/authority blocks
consequential decisions/actions, not an otherwise valid read/propose step. Missing
close evidence/acceptance blocks completion. Source-read failure stays a failure,
never proof of absence. No fallback may remove these controls.

## Publication, current selection and history

**Roles.** D11-B proposes one runtime-controlled profile `synthetic_pack_publication.v1`
with canonical human `identity_pack_reviewer_demo`, tenant `tenant_intake_demo`, full
North/South read scopes and **North preparation-publication scope only**, status and
UTC validity period. The profile content/hash and server-selected identity are retained
with each decision. This fixed, purpose-specific allowlist is not a catalog editor,
delegation system or general authority policy. Reuse strict identity validation;
reject contradictory identities, unknown/revoked/expired actors and scope excess.
Selecting its visibly synthetic seat is not production authentication.

The intake operator may propose/describe but has no publication grant. The publication
reviewer may explicitly publish, supersede or withdraw preparation selection only.
A real field/variant/policy owner remains unknown; no synthetic seat can approve their
business rules. D11-B permits no client-authored executable rules. Source/variant/
consequential rule slots remain `null`/disabled unless separately approved contracts
and scope exist; enabling them is outside this decision. The profile is trusted
server configuration shipped only after D-036 acceptance, never supplied by a caller.
A changed profile hash requires fresh publication approval for current selection.
For a given tenant/pack ID,
each version maps to exactly one artifact hash forever; changed content needs a new
version. A supported old template may be selected only through explicit rollback.

**Artifact.** Deterministically assemble one fixed template with current scoped
Discovery material and explicit unknowns. The embedded steps/rules/proof requirements
are the template content, bound by the complete artifact hash and template version;
no additional template-hash registry is needed. Bind the basis
material hash, Case C/head, intake receipt/bundle/source revision, Case-wide Discovery
revision/head, supporting business input hashes and complete interpreter tuple.
Require a current selected-record `discovery_description` confirmation, solely to
establish that input's descriptive review; a separate publication action is still
mandatory. No inferred owner, authority, date, ID or default rule enters the artifact.
The worked JSON is unapproved despite its synthetic descriptive confirmation.

**Read.** Candidate, diff, selection/history and export GETs derive from a consistent
read-only database snapshot. No writer lock, ID reservation, preview row, revision
or durable clock write. The current-use result is derived separately from historical
publication; an old approval or client hash never grants current permission.

**Command (proposed strict v1).** One publication POST accepts only operation
`publish | rollback | withdraw`, pack ID, exact candidate/target artifact hash,
expected pack-journal revision/head, expected basis bindings and profile hash,
reviewed effective-until instant/timezone, reason and idempotency key. `withdraw`
requires the exact selected artifact and head; no new basis/effectivity. `rollback`
references a retained artifact; it cannot submit rewritten content. Operation-specific
schemas reject extra identity, approval, policy, success or executable-content fields.
The server recomputes all hashes from canonical material. No endpoint exists yet.

Under the existing writer transaction: look up the trusted tenant/pack/operation/key
first; exact retry returns its original result, changed body conflicts. Then validate
expected pack head, current profile/identity/scope/time, current Case/Discovery/business
inputs and all disabled-action constraints. Publication starts at server evaluation
time; expiry must be later and within the profile grant. No scheduled or backdated
activation. The recorded time must not precede the prior pack entry or any bound
input; relevant clock regression fails closed. C/R/S are unchanged. Only the pack
stream and existing writer coordination revision advance.

Append one entry with command/fingerprint/key, full immutable artifact (or existing
artifact reference for withdraw/rollback), exact input material/manifest and immutable
evidence references, review purpose,
canonical actor/profile/evaluation time, validation versions/result, predecessor/hash
and selected-version result. Its relational indexes must agree with JSON and hashes;
read back integrity before commit. All or nothing on failure. Retain enough ordered
input references to reconstruct the original Discovery/intake
archive from canonical histories; do not copy original source bytes into the journal.
The portable exporter includes those unchanged bytes and nested archives. Successful
no-op metadata stays exportable but outside business dependency/consent hashes.
First successful commands always reserve their key atomically. A fresh-key attempt
to publish an already selected identical version returns a non-success `NO_CHANGE`;
it creates no binding or receipt. Exact retries of successful commands never write,
even after supersession/expiry; their response is explicitly historical, not permission.
No universal idempotency service or durable drafts are needed.

**Selection and staleness.** Journal revision is separate from C/R/S and Discovery's
Case-wide revision. Initial revision 0 selects nothing. A successful publish at 1
selects artifact A; publication B at 2 supersedes A for future use only. Any content,
scope, dependency or profile change invalidates a reviewed submission. Preserve
Discovery's conservative business-input invalidation; no-op command bookkeeping
is not business material. Any relevant C/Discovery head change requires refresh and
fresh publication approval, even if visible fields or material hash look unchanged.
No automatic approval carry-forward. Published A remains historical when stale,
expired, withdrawn or superseded; it cannot start new work. Scope expansion beyond
the approved profile is denied, not merely solved by a new hash.

**Rollback.** Append a new explicit selection entry with current reviewer authority,
current expected stream head and original artifact hash. The old artifact's complete
basis must still be current and compatible. Otherwise propose a new version using
the old template with fresh inputs, then review/publish it. A conservative rollback
that is refused is preferable to restoring stale consent. Withdraw can remove current
selection even when its business basis is stale; it still checks current publication
reviewer and exact stream head. Neither operation rewrites old entries or resurrects
a revoked grant. Existing Cases/reviews/attempts retain their original bindings.

**Replay/export.** Reconstruct original artifacts, selection fold and historical
validation under recorded versions, trusted snapshots and time. Validate dependency
hashes/anchors and chronological admissibility, not only a self-consistent supplied
prefix. Preserve canonical Case/intake/Discovery histories; equal timestamps do not
prove cross-journal ordering. A portable pack export nests the unchanged supported
Discovery/intake archive with the pack stream/profile snapshots; its outer hash does
not replace nested integrity validation. Historical v1 Discovery material keeps its
v1 meaning; new publication uses current v2. Unknown interpreters fail closed, including
Node/tzdata mismatch; retain Node **24.19.0 / 2026b** for existing archives. No general
restore endpoint or identity-status-history system. Complete-dataset disposal still
ends replay under D-034; real data/private knowledge is not authorized for this appliance.

## Reproduce the example basis

This uses the existing **disposable** local PostgreSQL/API test host, not an evaluator's
Case. Its one descriptive confirmation is test-generated, not proof of human inspection.
No pack command runs. With Node 24.19.0, installed dependencies, local PostgreSQL and
`D9_POSTGRES_URL` pointing to a disposable loopback test database:

```sh
pnpm build
D9_POSTGRES_URL=postgresql://fieldruntime:local-evaluation-only@127.0.0.1:55432/postgres node --input-type=module <<'JS'
import assert from "node:assert/strict";
import { readFile } from "node:fs/promises";
import { intakeHost } from "./tests/helpers/intake-postgres.mjs";
import { intakeInput } from "./tests/helpers/intake.mjs";
import { discoveryPath, reviewPath, discoveryCommand } from "./tests/helpers/discovery.mjs";
import { sha256Json } from "./dist/packages/contracts/src/index.js";
const example = JSON.parse(await readFile("docs/examples/d11-invoice-dispute-pack.proposed.json", "utf8"));
assert.equal(sha256Json(example.artifact), example.artifact_hash);
const cleanup = [];
try {
  const h = await intakeHost({ after: f => cleanup.push(f) });
  const view = await h.prepare(await intakeInput("d11-example-prepare"));
  const receipt = (await h.ok("/v1/intake/commits", await h.selection(view, 0, { key: "d11-example-commit" }))).receipt;
  const path = discoveryPath(view, receipt.case_id);
  let brief = await h.ok(path);
  await h.ok(reviewPath(view), discoveryCommand(brief, "d11-example-confirm", "confirm"));
  brief = await h.ok(path);
  const basis = example.artifact.discovery_basis;
  assert.deepEqual(brief.binding, basis.binding);
  assert.deepEqual(brief.material.manifest, basis.manifest);
  assert.deepEqual(brief.material.sources, example.artifact.evidence.citations);
  const archive = await h.ok(path + "&representation=export");
  assert.equal(sha256Json(archive), example.example_basis_export_hash);
  const before = await h.snapshot();
  await h.restart();
  assert.deepEqual((await h.ok(path)).binding, basis.binding);
  assert.equal(sha256Json(await h.ok(path + "&representation=export")), example.example_basis_export_hash);
  assert.deepEqual(await h.snapshot(), before);
  console.log("PASS: example hash, canonical basis, citations, restart and read-only export; no pack published");
} finally {
  for (const close of cleanup.reverse()) await close();
}
JS
```

The port is the existing local test-host example, not the appliance default; adjust
only the connection string for your disposable PostgreSQL. The helper drops its own
random test schema. Example verification is evidence for existing D9/D10 behavior and
document consistency, not implemented D11 publication or passed T1–T9.
